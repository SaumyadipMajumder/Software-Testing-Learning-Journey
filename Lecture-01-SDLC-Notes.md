Q) What is the difference between Verification and Validation?
Ans: The difference between verification and validation is that verification does the review of the process before executing or starting the development of the software itself, where we review walkthrough and inspect every process of the documentation from customer requirement specifications, system requirement specifications, HLD, and LLD. Whereas validation starts after the development of the software has done, and we start with the testing the built software itself with unit testing, integration testing, system testing, and user agreement testing. In simple terms, we, in verification, we verify the document before creating the development of the software itself, while in validation, we validate the software that has been developed itself, with the process of different testing.

Q) What is the difference between Static Testing and Dynamic Testing?
Ans: Static testing is basically the testing of the documents itself, where we like review the documents of different processes such as CRS, SRS, HLD, LLD documents, walk through with them, inspect them. That is a static process. Whereas in dynamic process, we test the software itself, where we have unit testing, integration testing, system testing, and UAT. In the static testing, because the whole process is static, it is the documents are itself static. But in the dynamic testing, we are running the software to check whether it behaves correctly.

Black box testing is done by the testers who test the software after it has been developed.

Q1. Review vs Walkthrough vs Inspection

Suppose your team has just finished writing the Software Requirement Specification (SRS) document.

Explain:

What is a Review?
What is a Walkthrough?
What is an Inspection?

Also tell me who usually conducts each one.

Answer: Review is a process where one person, which can be the author who created the document itself, review the whole process from the requirement analysis documents, the test analysis document, code analysis documents, the whole process can be tested through the design analysis. Everything can be tested by one person. It is not a formal process. It can be done anytime with one person involved in it, which most of the time is the author themselves who created these documents. Walkthrough is also a very informal process. It can be done with a minimum of two people, where the author reads the whole document that they have created with other person to take the feedback of the process itself. It is not pre-planned or a meeting type. It is done within an informal process of reviewing the documents with some other person. While inspection is a more formal process, it is done with pre-planned at least three people to more than eight. It has one person, the author or the reader, the recorder/scribe, inspectors/reviewrs and one moderator. It is done in a very meeting process where we go through every process of the documentation and inspect or review them in front of a team where the author reads the whole process, document, and if there is any query, if there is any type of problem, the writer writes those problems, and the moderator, basically they host the whole process of this inspected meeting.

Q4. Integration Testing (Concept)
Suppose:

Login Module
Payment Module
Order Module

All three work perfectly by themselves. But after login, payment fails because user information isn't passed correctly. What level of testing finds this? Why?

Answer: Integration Testing, because each module works individually, but the data transfer between the Login and Payment modules is failing. Integration Testing specifically checks interactions between modules. 
Login module works.
Payment module works.
But their interaction fails.
That is exactly what Integration Testing is designed to catch.
